# 네이버 플레이스 영업 DB 수집기 V1.2

지역 기반 소상공인 영업을 하는 광고대행사, POS/키오스크 영업자, 식자재 유통업체를 위한 **영업 DB 엑셀 수집 도구**입니다.

GUI 실행 진입점인 `app.py`를 기준으로 동작합니다. 공식 법정동 데이터를 기준으로 시도·시군구·법정동(다중 선택, 가나다순 표시)과 키워드를 선택하면 검색 조합을 자동으로 생성하고, 브라우저가 검색 과정에서 정상적으로 수신한 목록 응답을 처리해 업체 데이터를 Excel로 저장합니다.

---

## 1. 핵심 방향

- GUI 기반 실행 (`app.py`)
- 지역(행정안전부 공식 법정동 Snapshot 기반 시도 + 시군구 + 법정동 다중 선택, §11) + 키워드 선택 → 검색 조합과 전체 목표 저장 개수를 자동 생성
- 브라우저가 검색 과정에서 정상적으로 수신한 응답을 처리해 업체 목록 데이터로 변환합니다. 별도의 HTTP 클라이언트로 네이버 엔드포인트를 직접 호출하는 구조는 사용하지 않습니다.
- 검색 결과 목록 화면만 사용하며, 카드를 클릭해 상세 화면으로 진입하지 않습니다(상세 페이지 미진입).
- 검색 조합 내부 중복 제거(검색 조합당 수집 상한) → 전체 검색 조합 전역 중복 제거(전체 목표 저장 개수) 2단계로 중복을 제거합니다.
- 전체 목표 저장 개수에 도달하거나 선택한 검색 조합을 모두 실행하면 종료합니다.
- CAPTCHA·요청 제한(429) 감지 시 우회하지 않고 즉시 중단하며, 그때까지 수집된 결과가 있으면 저장합니다.
- Excel 저장을 통한 즉시 영업 활용
- 본 프로그램은 네이버 공식 제품이거나 네이버와 제휴한 제품이 아닙니다.
- 참고: 이전 버전의 `빠른 수집(모바일)`/`상세 수집(PC·전화·SNS)` 엔진 코드는 삭제하지 않고 내부 롤백 경로로 보존되어 있으나, 현재 UI 기본 실행 경로는 아닙니다.
- **수집 모드는 2가지이며 화면에서 선택합니다(§2/§9).** "빠른 기본 수집"은 목록 응답만으로 채워지고, "홈페이지·SNS 포함 수집"은 목록 수집 후 업체별 홈페이지 보강 단계가 추가로 붙어 그만큼 더 걸립니다.
- **지역 선택은 행정안전부 공식 법정동 Snapshot(§10/§11) 하나만 사용합니다.** 앱 실행 중 행안부 API를 호출하지 않으며(로컬 파일만 읽음), 전국 시도/시군구/법정동을 전부 선택할 수 있습니다. 역·상권/세부업종 보조 검색 기능은 제거했으며, 최종 검색 조합은 공식 법정동 선택 + 키워드만으로 구성됩니다. 시군구·법정동 목록은 가나다순으로 표시됩니다(§11). 네이버가 반환하는 주소를 공식 지역과 비교하는 지역 exact 필터·Provider Alias 정책이 적용되어 있으며(지역 밖 결과는 최종 Excel에서 제외), 네이버 검색어 명칭 호환성은 실측된 사례(§11)에 한해 반영돼 있습니다.
- **새로오픈 업체만 수집 필터를 사용할 수 있습니다(§11).** 체크하면 네이버가 제공하는 새로오픈 전용 목록만 수집하며, 새로오픈 업체 수가 목표보다 적으면 실제 확보된 개수로 정상 종료됩니다(오류 아님).

검색 흐름:

```text
https://map.naver.com/v5/search/{지역+업종}
  -> 검색 결과 목록 화면에서 브라우저가 정상적으로 수신한 응답을 관찰
  -> 응답에 포함된 업체 목록 데이터를 그대로 사용(카드 클릭·상세 페이지 진입 없음)
```

## 2. 수집 필드

`통합_결과` 시트 기준 14컬럼:

- 업체명
- 업종
- 새로오픈여부
- 방문자리뷰수
- 블로그리뷰수
- 총리뷰수
- 주소
- 대표전화
- 플레이스 URL
- 수집일
- 홈페이지
- 인스타
- 블로그
- 추가 링크

> `place_id`와 `source_city`/`source_district`/`source_subregion`/`source_layer`/`source_query`, 그리고 상세정보 보강 진단 필드(`home_*`)는 중복 제거·내부 진단용 필드이며 **Excel에는 노출하지 않습니다**. 사용자에게는 위 14컬럼만 제공됩니다.

필드별 참고:

- 업체명/업종/주소/대표전화/플레이스 URL/수집일은 검색 목록 응답 값을 기본으로 합니다. 주소는 지역명 중복 표기를 정리하되 건물명은 보존합니다. 값이 전혀 없으면 빈칸일 수 있습니다.
- **방문자리뷰수/블로그리뷰수/총리뷰수는 서로 다른 값입니다.** 방문자리뷰수·블로그리뷰수 각각 실제로 확인되지 않은 경우(응답에 값 자체가 없음) 값을 0으로 임의 처리하지 않고 빈칸으로 남깁니다(실제 리뷰가 0건인 경우와 "확인되지 않음"을 구분). 총리뷰수는 방문자리뷰수와 블로그리뷰수가 **둘 다 확인됐을 때만** 두 값을 더해 채우며, 하나라도 확인되지 않으면 총리뷰수도 빈칸입니다.
- **대표전화는 개인 휴대전화(010/011/016~019, 국제표기 +82-10 등)를 절대 채택하지 않습니다.** 일반 유선/대표번호 → 0507 등 공식 가상번호 → 그 외 사업장 공개 번호 순으로만 채택하며, 채택 가능한 값이 없으면 빈칸입니다. 개인 이동전화 원문은 Excel·로그·진단 파일 어디에도 남기지 않습니다.
- **홈페이지/인스타/블로그/추가 링크는 사업장이 플레이스에 스스로 공개한 링크를 도메인 기준으로 분류한 값입니다**(개인정보 아님, 네이버 자체 지도/예약/스마트스토어/광고/talktalk 리다이렉트 도메인은 제외). 대표 3링크(홈페이지·인스타·블로그) 외 채널(카카오채널·유튜브·페이스북·스마트스토어·기타 및 2번째 이후 홈페이지/인스타/블로그)은 모두 **추가 링크** 컬럼에 `[채널명] URL` 형식으로, 여러 건이면 셀 안에서 줄바꿈으로 구분해 담습니다. 업체별로 링크가 없으면 해당 컬럼은 빈칸일 수 있으며, 4개 링크 컬럼이 전부 빈칸이어도 그 자체는 수집 실패가 아닙니다(§9).
- **새로오픈여부는 O(신규 오픈 확인)/X(아님)/빈칸(확인되지 않음) 3가지 상태입니다.** 확인되지 않은 값을 X로 임의 단정하지 않습니다.
- **"홈페이지·SNS 포함 수집" 모드에서만** 홈페이지/인스타/블로그/추가 링크와 대표전화(목록에서 공란인 경우만)가 place_id 기반 홈페이지 보강으로 채워집니다(§9). "빠른 기본 수집" 모드에서는 이 보강 단계 자체가 실행되지 않으므로 위 4개 링크 컬럼은 목록 응답에 값이 있는 경우를 제외하면 대부분 빈칸입니다.

제외 항목:

- 영업시간
- 평점
- 대표자명
- 개인 휴대폰 번호
- 개인 이메일

## 3. 결과물

수집 결과가 1건 이상이면 Excel 파일로 저장합니다. **수집 결과가 0건이면 Excel 파일을 만들지 않습니다**(빈 파일을 남기지 않음).

실제 저장 경로 예시(파일명은 화면에서 지정한 저장 경로의 파일명을 기준으로, 실행 시각 타임스탬프가 자동으로 붙습니다 - 열려 있는 파일과의 덮어쓰기 충돌 방지):

```text
output/<파일명>_YYYYMMDD_HHMM.xlsx
```

`통합_결과` 출력 컬럼(14컬럼):

| 컬럼명 | 설명 |
|---|---|
| 업체명 | 검색 목록 응답 기준 업체명 |
| 업종 | 카테고리 (추출 불안정, 빈 값 허용) |
| 새로오픈여부 | O/X/빈 값 3상태(§2. 수집 필드, 확인 안 되면 X로 단정하지 않음) |
| 방문자리뷰수 | 확인되지 않으면 빈 값(0과 구분, §2. 수집 필드) |
| 블로그리뷰수 | 확인되지 않으면 빈 값(0과 구분, §2. 수집 필드) |
| 총리뷰수 | 방문자+블로그가 모두 확인됐을 때만 채워짐 |
| 주소 | 목록 기준 주소, 지역명 중복 제거·건물명 보존(값 없으면 빈 값) |
| 대표전화 | 개인 휴대전화 제외, 일반 유선/공식 가상번호 우선(값 없으면 빈 값) |
| 플레이스 URL | 업체 상세 페이지 URL |
| 수집일 | 수집 실행일 (YYYY-MM-DD) |
| 홈페이지 | 대표 외부 링크 중 인스타/블로그가 아닌 홈페이지(없으면 빈 값, §9는 home_sns 모드에서만 채움) |
| 인스타 | `instagram.com` 링크(없으면 빈 값) |
| 블로그 | `blog.naver.com` 등 블로그 링크(없으면 빈 값) |
| 추가 링크 | 대표 3링크 외 채널(카카오채널/유튜브/페이스북/스마트스토어/기타 등) - `[채널명] URL` 형식, 여러 건이면 줄바꿈으로 구분(없으면 빈 값) |

Excel은 `통합_결과`, `원본_모바일`, `원본_PC` 3개 시트로 저장됩니다(`src/exporter.py` 기준, 시트 구조 무변경).

- `통합_결과`: 주 산출물 시트이며 위 14컬럼 데이터가 들어갑니다.
- `원본_모바일`, `원본_PC`: 과거 모바일/PC 분리 수집 구조를 유지하기 위한 시트입니다. 현재 기본 수집 경로는 목록 응답 하나만 사용하므로 이 두 시트는 **항상 헤더만 있는 빈 시트**로 저장됩니다.

## 4. 수집 개수와 중단·저장 정책

두 입력값은 서로 다른 의미이며 독립적인 양의 정수입니다.

| 입력값 | 의미 | 기본값 |
|---|---|---|
| 검색 조합당 수집 상한 | 검색 조합(지역+업종) 하나에서 중복 제거 후 사용할 최대 개수 | 30 |
| 전체 목표 저장 개수 | 여러 검색 조합 결과를 전역 중복 제거한 뒤 최종 저장할 목표 개수 | 300 |

- **전체 목표 저장 개수는 최대 목표값이며, 지역·업종·검색 결과 및 서비스 상태에 따라 목표에 미달할 수 있습니다.** "300개 보장"을 의미하지 않습니다.
- 목표 개수에 도달하면 남은 검색 조합은 실행하지 않고 그 시점까지의 결과를 저장합니다.
- 검색 가능한 고유 업체 수가 목표보다 적으면 선택한 검색 조합을 모두 실행한 뒤, 그때까지의 결과를 저장합니다(목표 미달 가능).

수집이 끝나는 경우와 저장 여부:

| 상황 | 저장 여부 |
|---|---|
| 전체 목표 개수 도달 | 저장 |
| 선택한 검색 조합을 모두 실행(목표 미달 가능) | 저장 |
| CAPTCHA(보안 확인) 감지 | 우회하지 않고 즉시 중단, 그때까지 결과가 있으면 저장 |
| 요청 제한(429) 감지 | 우회하지 않고 즉시 중단, 그때까지 결과가 있으면 저장 |
| 브라우저 페이지 오류 | 즉시 중단, 그 이전까지의 결과가 있으면 저장 |
| 사용자 중지 버튼 | 즉시 중단, 그때까지 결과가 있으면 저장 |
| 홈페이지·SNS 보강(§9, home_sns 모드) 중 CAPTCHA/HTTP 403·405·429 감지 | 우회·재시도 없이 보강 전체 즉시 중단, 그때까지 보강된 결과 + 아직 보강하지 않은 원본 목록 결과를 함께 저장 |
| 홈페이지·SNS 보강(§9) 중 요청 업체와 응답 업체 불일치(place_id mismatch) 감지 | 해당 업체는 병합하지 않음(재시도 대상도 아님), 다른 업체는 계속 진행 |
| 홈페이지·SNS 보강(§9) 중 일시적 오류(타임아웃/5xx/응답 없음 등) | 재시도 금지 사유(차단/불일치)가 아니면 안정화 대기 후 업체당 최대 1회 재시도(§9) |

- **위 어떤 경우든 수집된 결과가 1건 이상 있을 때만 저장됩니다.** 결과가 0건이면 어떤 경우에도 Excel 파일을 만들지 않습니다("항상 부분 저장된다"는 의미가 아닙니다).
- "홈페이지·SNS 포함 수집" 모드에서는 목록 수집이 끝난 뒤 §9의 홈페이지·SNS 보강이 이어서 진행되며, 목록 단계에서 이미 CAPTCHA/429가 감지되어 중단된 경우에는 보강을 시작하지 않습니다(이미 차단이 감지된 직후 추가 요청을 보내지 않기 위함). "빠른 기본 수집" 모드에서는 이 보강 단계 자체가 없으므로 목록 수집만으로 즉시 저장됩니다.
- Excel 저장 자체(디스크 쓰기 등)에서 오류가 발생하면 저장되지 않을 수 있습니다. 이 경우 프로그램은 저장 성공 문구를 표시하지 않고 저장 실패를 화면에 알립니다.
- CAPTCHA/429 감지 시 프로그램은 이를 해결하거나 회피하려고 시도하지 않습니다. 짧은 시간에 반복 실행하지 말고 잠시 후 다시 시도하세요.

### Windows Native Browser + CDP

2026-07-21부터 기본 브라우저 backend는 Playwright 번들 Chromium을 직접 띄우는 방식(`launch`)이 아니라, **Windows에 설치된 네이티브 Microsoft Edge 또는 Google Chrome을 백그라운드로 실행한 뒤 CDP(Chrome DevTools Protocol)로 연결하는 방식(`native_cdp`)**입니다.

- **요구사항**: Windows에 Microsoft Edge 또는 Google Chrome 중 하나 이상이 설치되어 있어야 합니다(대부분의 Windows 10/11에는 Edge가 기본 설치되어 있음).
- **탐색 순서**: 1) 사용자가 지정한 custom browser 경로 → 2) Microsoft Edge → 3) Google Chrome. 아래 경로를 순서대로 탐색합니다.
  - Edge: `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe` → `C:\Program Files\Microsoft\Edge\Application\msedge.exe` → `%LOCALAPPDATA%\Microsoft\Edge\Application\msedge.exe`
  - Chrome: `C:\Program Files\Google\Chrome\Application\chrome.exe` → `C:\Program Files (x86)\Google\Chrome\Application\chrome.exe` → `%LOCALAPPDATA%\Google\Chrome\Application\chrome.exe`
  - 둘 다 찾지 못하면 Playwright 번들 Chromium으로 조용히 대체하지 않고, 탐색한 경로와 해결 방법이 포함된 명확한 오류를 표시합니다.
- **전용 profile**: 사용자의 평소 Edge/Chrome 프로필이 아니라 `%LOCALAPPDATA%\NaverPlaceSalesDbCrawler\browser_profiles\{edge|chrome}` 전용 프로필을 사용합니다. 동일 프로필을 두 프로세스가 동시에 사용하려 하면 `profile_in_use` 오류로 명확히 차단됩니다(다른 backend로 조용히 전환하지 않음).
- **디버깅 포트**: 고정 포트가 아니라 매 실행마다 `127.0.0.1`에서만 열리는 임시(동적) 포트를 사용합니다. 외부 네트워크 인터페이스에는 노출되지 않습니다.
- **정상 종료**: 프로그램이 실행한 브라우저 프로세스(PID)만 종료합니다. `taskkill /IM`처럼 이미지 이름으로 모든 Edge/Chrome 창을 닫는 방식은 사용하지 않으므로, 사용자가 평소 쓰던 Edge/Chrome 창에는 영향이 없습니다.
- **launch backend(개발·테스트용)**: 기존 Playwright 번들 Chromium 실행 방식은 삭제되지 않고 개발·테스트 전용 fallback으로 보존되어 있습니다. 필요 시 환경 변수 `PCCRAWLER_BROWSER_BACKEND=launch`로 명시적으로 전환할 수 있으며(배포 EXE에서는 이 환경 변수가 무시되고 항상 `native_cdp`가 사용됩니다), 프로덕션 배포 시에는 사용하지 않습니다.
- **문제 해결**:
  - `BrowserExecutableNotFoundError`: Edge 또는 Chrome을 설치하거나, 환경 변수 `PCCRAWLER_BROWSER_PATH`로 실행 파일 경로를 직접 지정하세요.
  - `profile_in_use`: 이미 실행 중인 다른 수집 프로세스가 끝날 때까지 기다린 뒤 다시 시도하세요.
  - `CdpStartupError`(CDP 준비 실패/timeout): 브라우저가 비정상 종료되었거나 포트가 막혀있을 수 있습니다. 잠시 후 다시 시도하세요.
- Native Browser + CDP 방식은 현재 Windows 환경과 검증 검색(서울특별시 강동구 천호동 카페)에서 Edge 2회·Chrome 2회 실측과 단일 Live 검증 모두 CAPTCHA·HTTP 403/405/429 없이 수집에 성공했으며, 기존 Playwright launch 환경(동일 검색에서 page 2 HTTP 405로 반복 중단)과 다른 결과를 보였습니다. 이는 모든 환경·검색어에서 항상 차단을 우회한다는 의미가 아니며, CAPTCHA·403·405·429 감지와 안전 중단 정책은 이 backend 교체와 무관하게 그대로 유지됩니다(§4. 수집 개수와 중단·저장 정책).

## 8. 목록 수집 엔진

**현재 `app.py`의 "수집 시작" 기본 동작은 Apollo/GraphQL-first 엔진(`ApolloFirstListCollector`)을 사용합니다**(`src/ui.py`가 `ApolloFirstListCollector`만 import하고, `_run_network_pipeline` 기본 `collector_factory`도 이 클래스입니다 - UI에 별도 토글은 없습니다). `ApolloFirstListCollector`(및 그 목록 수집 함수 `collect_apollo_first_list_query`, `src/pc/network_browser_collector.py`)는 1페이지는 메인 `placeList(...)` GraphQL 응답만 파싱하고(DOM 스크롤 없음), 2페이지 이후는 자연 발생하는 GraphQL 응답을 관찰해 수집합니다. `enrich_detail`/`enrich_detail_ssr`을 정의하지 않으며, 홈페이지·SNS 보강은 이 클래스가 아니라 이 세션이 완전히 종료된 뒤 별도로 `src/pc/home_enrichment.py`가 담당합니다(§9).

이전 기본 엔진이었던 아래 **DOM-first 엔진(`DomMembershipCollector`)은 코드에 그대로 보존**되어 있으나, 현재 `src/ui.py`는 이 클래스를 import하지 않으며 기본 경로로 실행되지 않습니다. 되돌리려면 코드에서 `collector_factory=DomMembershipCollector`를 직접 import해 명시적으로 지정해야 합니다(현재 UI에는 이 전환을 위한 화면 옵션이 없습니다). 그보다 더 이전 엔진(`NetworkBrowserCollector`/`collect_network_query`, Network 응답 관찰 기반)도 코드에 보존되어 있으며 동일한 방식으로 명시 지정해야만 사용됩니다.

- **DOM-first membership(`DomMembershipCollector`, 현재 비활성 롤백 경로)**: 검색 목록 화면(`iframe#searchIframe`)에서 검증된 scrollBy 증분 스크롤(`cdp_validation_tests/comprehensive_cdp_tester.py` 기준 - scrollHeight/row수/업체명수 3개 지표가 함께 안정될 때까지 단일 `frame.evaluate()` 안에서 반복)로 리스트를 끝까지 렌더링한 뒤, `li.UEzoS.rTjJo` row를 그대로 최종 업체 목록(membership)과 표시 순서로 사용합니다. Network 응답과 `window.__APOLLO_STATE__`는 그 DOM 업체의 구조화 필드(업종/리뷰수/주소 등)를 보강하는 용도로만 쓰이고, DOM에 없는 Network/Apollo 항목은 결과에 추가되지 않습니다.
- **React Fiber 기반 place_id 식별자(2026-07-21 추가)**: DOM 카드의 링크(`<a href>`)는 실측 결과 전부 `href="#"`(placeholder)라 URL에서 업체 ID를 안정적으로 얻을 수 없습니다. 대신 React가 각 DOM 노드에 심어두는 내부 속성(`__reactFiber$*`/`__reactProps$*` - 접두사 뒤 임의 문자열은 페이지 로드마다 바뀌므로 `Object.keys()`로 동적 탐색)에서 실제 업체 ID(`item.id`/`item.apolloCacheId`)를 읽습니다. 이 속성은 **React의 비공개 내부 구현이며 공식 API가 아닙니다** - Naver Map 프론트엔드 구조가 바뀌면 이 경로가 깨질 수 있습니다. 이를 대비해 다음 guard를 둡니다.
  - 1차: 알려진 경로(fast path)에서 `item.id`와 `item.apolloCacheId`를 각각 확인하고, 둘 다 있는데 값이 다르면 **CONFLICT로 판정하고 임의로 하나를 선택하지 않습니다**.
  - 2차(fast path 실패 시만): 깊이·방문 객체 수·순환 참조를 제한한 범위 탐색(bounded search)으로 `id`류 이름의 값을 찾되, 서로 다른 값이 2개 이상이면 역시 CONFLICT로 판정합니다.
  - 3차(그래도 없을 때): DOM anchor href 파싱을 최후 수단으로 시도합니다.
  - 숫자가 아니거나 비정상적으로 짧거나/긴 값은 애초에 후보로 인정하지 않습니다.
  - 어떤 방법으로도 확정하지 못해도(UNRESOLVED) **업체 row 자체는 삭제하지 않습니다** - 업체명/업종 등 DOM에서 바로 얻은 값은 그대로 보존됩니다.
- 단일 검색어, 최대 5페이지, 목표 300건 계약입니다.
- **상세 필드 채움률(2026-07-21 Live 검증 300건 실측 기준, 상세정보 enrichment 미적용 시)**: place_id 식별이 안정화된 뒤(300/300 확보, 충돌·미해결 0건) 업체명·업종·수집일 300/300, 주소 300/300, 리뷰수 285/300, **플레이스 URL 300/300**(§9의 범용 URL 생성)까지는 상세 페이지를 방문하지 않아도 채워집니다. 대표전화·홈페이지·인스타·블로그는 검색 목록 API 응답 자체에 그 필드가 거의 없어(일부 업체는 Network 응답에 전화번호가 실려 있기도 함이 확인됨) 상세정보 enrichment(§9) 없이는 낮게 유지됩니다.
- **안전 중단**: 기존과 동일하게 CAPTCHA·HTTP 403·405·429·iframe/list container 소실 시 즉시 중단하고 그때까지 결과를 보존합니다. 페이지 전환 완료는 "기대 페이지 번호와 실제 활성 페이지 번호 일치 + DOM top-10 이름 signature 변화"를 모두 확인해야 인정합니다(페이지 번호만으로 판단하지 않음).
- **문제 해결**: 300건 미만으로 끝나면 성공으로 표시하지 않습니다. CAPTCHA/HTTP 오류/전환 실패/식별자 확보 실패는 각각 별도로 진단 기록에 남습니다(자동 보완이나 재시도를 하지 않음).

## 9. place_id 기반 홈페이지·SNS 보강(2026-07-27 재시도/진단 정책 확정, `src/pc/home_enrichment.py`)

**이 단계는 "홈페이지·SNS 포함 수집" 모드를 선택했을 때만 실행됩니다.** "빠른 기본 수집" 모드에서는 이 단계 자체가 호출되지 않으며 place_id 기반 home HTML 요청이 0회입니다(`src/ui.py`가 `collection_mode == "home_sns"`일 때만 호출).

```text
목록 DOM 수집 → 목록 Network/Apollo 보강 → 모든 검색 조합 완료
  → 전체 place_id 전역 중복 제거(§4) → [home_sns 모드만] 최종 고유 업체별 홈페이지·SNS 보강(본 절)
  → Excel 저장(14컬럼, §2/§3)
```

목록 수집에 쓰인 브라우저 세션이 완전히 종료된 뒤, **같은 사용자 프로필 디렉터리를 가리키는 새 Native Edge/Chrome CDP 연결**을 별도로 열어(§6, 쿠키 "값"을 코드로 복사하지 않고 프로필이 디스크에 이미 들고 있는 세션을 그대로 재사용) 고유 업체마다 home HTML GET 요청으로 홈페이지/인스타/블로그/추가 링크(및 목록에서 공란인 대표전화만)를 보강합니다.

- **동시성/재시도 정책**: 1차 순회는 동시성 2로 고유 place_id당 최대 1회 요청합니다. 1차에서 실패한 업체 중 **재시도 가능한 원인**(timeout/request_error/HTTP 5xx/빈 응답/Apollo·Base·Parent 정보 없음)만 3초 안정화 대기 후 동시성 1로 업체당 최대 1회 재시도합니다 - 업체당 최대 요청 2회, 성공한 업체는 재요청하지 않습니다. 1차 실패율이 대상 수의 10%를 초과하면 재시도 자체를 진행하지 않습니다(대량 실패 안전장치).
- **재시도 금지(차단) 사유**: HTTP 403/405/429, CAPTCHA, place_id 불일치, 사용자 중지는 재시도하지 않습니다. CAPTCHA/403/405/429가 감지되면 신규 요청 스케줄링을 즉시 중단하고(재시도 큐도 만들지 않음), 이미 처리된 결과와 아직 처리하지 않은 원본 목록 결과는 그대로 저장합니다(§4).
- **필드 확보 방식**: 받아온 HTML 안의 `window.__APOLLO_STATE__` 값을 안전하게 파싱해 업체 기준 항목(Base)과 연결된 상세 항목(Parent)을 결합한 뒤 §2의 필드로 매핑합니다.
- **업체 일치 확인**: 응답에서 확인한 업체 ID가 요청한 업체와 정확히 같을 때만 값을 채택합니다. 다르면 그 업체만 병합하지 않고 재시도도 하지 않습니다(다른 업체는 계속 진행).
- **링크 0개도 성공**: HTTP/Apollo/Base/Parent/업체 일치가 모두 정상이면, 그 업체가 홈페이지·SNS를 실제로 등록하지 않아 4개 링크 컬럼이 전부 빈칸이어도 그 자체는 실패가 아닙니다.
- **병합 원칙**: 항상 업체 ID(place_id) 기준으로만 병합하며, 업체명/업종/새로오픈여부/방문자·블로그·총리뷰수/주소/플레이스 URL/수집일 등 목록 단계에서 이미 확정된 핵심 필드는 절대 덮어쓰지 않습니다(허용 목록: 홈페이지/인스타/블로그/추가 링크/공란이었던 대표전화만 채움).
- **실패해도 행 보존**: 최종까지 실패한 업체도 목록 단계에서 확보한 값 그대로 Excel 행에 남습니다(행 삭제 없음) - 최종 Excel 행 수는 항상 목록 수집 결과 수와 같습니다.
- **사용자 중지**: 보강 중에도 언제든 중지할 수 있으며, 중지 시 새 요청만 즉시 멈추고 이미 처리된 결과·아직 처리하지 않은 원본 결과는 모두 보존한 뒤 그때까지의 결과를 저장합니다.
- **실패 진단 기록**: 모든 시도(1차+재시도)와 최종 실패 업체(업체명/place_id/HTTP/실패 사유/재시도 여부)를 `logs/diagnostics/home_enrichment_<실행시각>.json`에 저장합니다. 쿠키/Authorization/토큰/요청 헤더 원문/HTML 원문/Apollo State 원문은 저장하지 않습니다.
- **진행 표시**: 목록 수집 진행률과는 별도로 "홈페이지/SNS 정보 수집 중 현재/전체(성공/실패)" 화면 상태 문구로 안내합니다.
- 기존 카드 클릭 기반 상세 수집(`src/pc/detail_scraper.py`)은 삭제되지 않았으며 legacy 롤백 경로로 그대로 보존되어 있으나, 현재 홈페이지·SNS 보강 경로에서는 사용하지 않습니다.

## 10. 법정동 공식 데이터 갱신(개발자용, `scripts/update_legal_dong_snapshot.py`)

**평소 프로그램(`app.py`) 실행은 행안부 API를 전혀 호출하지 않습니다.** 최종 사용자는 API 키가 필요 없으며, 이 스크립트는 개발자가 공식 법정동 데이터를 미리 갱신해두는 별도 도구입니다. 프로그램은 이 도구가 만든 로컬 Snapshot 파일(`data/legal_dong_snapshot.json`)을 읽기 전용으로 사용합니다(§11. 공식 법정동 지역 선택).

- **개발자용 환경변수**: `.env`에 `DATA_GO_KR_SERVICE_KEY=<공공데이터포털에서 발급받은 키>`를 설정해야 합니다(`.env.example` 참고). 키가 없으면 스크립트는 네트워크 호출 없이 안내만 출력하고 종료합니다.
- **Dry Run(기본, snapshot 미변경)**:
  ```powershell
  .venv\Scripts\python.exe scripts\update_legal_dong_snapshot.py
  ```
  행안부 API를 조회해 현재 `data/legal_dong_snapshot.json`과 비교한 변경 보고서만 만들고, 기존 Snapshot 파일은 수정하지 않습니다.
- **Apply(검증된 결과로 Snapshot 교체)**:
  ```powershell
  .venv\Scripts\python.exe scripts\update_legal_dong_snapshot.py --apply
  ```
  검증을 통과한 경우에만 원자적으로 Snapshot을 교체합니다(기존 파일이 있으면 먼저 백업). Dry Run과 달리 실제로 파일을 씁니다.
- **Snapshot 경로**: `data/legal_dong_snapshot.json`
- **변경 보고서 경로**: `logs/diagnostics/legal_dong_snapshot_update_<실행시각>.json`(신규/명칭변경/삭제후보 요약만 포함, 인증키·전체 요청 URL은 저장하지 않음)
- **서비스키를 Git에 올리지 마세요** - `.env`는 `.gitignore`에 포함되어 있으며, `.env.example`에는 실제 키 값을 채우지 않습니다.
- 행안부 공식 데이터가 실제로 변경되면 Dry Run 보고서의 신규/명칭변경/삭제후보 내역을 검토한 뒤에만 `--apply`로 반영하세요 - 삭제후보(REMOVED_CANDIDATE)는 자동으로 삭제되거나 비활성 처리되지 않습니다.

## 11. 공식 법정동 지역 선택(UI)

왼쪽 패널 "1. 지역 선택"에서 `data/legal_dong_snapshot.json`(§10) 기반으로 **시도 → 시군구 → 법정동(다중 선택, 팝업)** 을 고릅니다. 앱 실행 중 이 기능은 행안부 API를 호출하지 않고 로컬 Snapshot 파일만 읽으며, 지역 선택 경로는 이 하나뿐입니다(예전에 있던 하드코딩된 시/도+구 다중 체크박스는 제거했습니다).

- **시도/시군구는 콤보박스 단일 선택**입니다. 시도를 바꾸면 시군구·법정동 선택이 초기화되고, 시군구를 바꾸면 법정동 선택이 초기화됩니다. 세종특별자치시처럼 시군구 계층이 없는 지역은 시군구 콤보박스가 비활성화되고 법정동을 바로 선택할 수 있습니다(지역명을 코드에 하드코딩하지 않고 데이터 구조로만 판단). **시군구 목록은 가나다순으로 표시됩니다**(OS locale에 의존하지 않는 정렬 - 공식 Snapshot 원본 파일의 레코드 순서/법정동 코드 자체는 바뀌지 않습니다).
- **법정동은 "법정동 선택" 버튼으로 여는 팝업에서 다중 선택**합니다(전체 선택/해제 제공, **가나다순 표시**). 법정동을 하나도 선택하지 않으면 시군구(시군구 없는 지역은 시도) 단위로 검색 조합 1개를 만들고, 여러 개 선택하면 법정동마다 가나다순으로 검색 조합을 만듭니다.
- **역·상권/세부업종 보조 검색 기능은 제거했습니다.** 최종 검색 조합(Query Queue)은 공식 법정동 선택 + 키워드만으로 구성됩니다.
- **"새로오픈 업체만 수집" 필터를 사용할 수 있습니다.** 체크하면 네이버 검색 결과 페이지에 함께 제공되는 새로오픈 전용 목록(일반 목록과 별도)만 수집하며, 일반 목록으로 조용히 대체하지 않습니다. 새로오픈 업체가 목표보다 적으면 실제 확보된 개수로 정상 종료됩니다(오류 아님). 지역 exact 필터·place_id 전역 중복 제거는 새로오픈 필터와 함께 그대로 적용됩니다.
- **전체 목표 저장 개수는 항상 자동 계산되며 직접 입력할 수 없습니다**(검색 조합당 수집 상한 × 최종 검색 조합 수 - 공식 법정동 선택의 중복 제거된 결과 기준). 입력창은 항상 읽기 전용(disabled)입니다.
- 두 수집 모드("빠른 기본 수집"/"홈페이지·SNS 포함 수집") 모두 동일한 검색 조합·새로오픈 필터·자동 계산된 목표 개수를 사용합니다.
- 세종특별자치시·전남광주통합특별시 등은 행정안전부 공식 명칭을 그대로 표시/사용합니다. 네이버가 반환하는 주소가 공식 명칭과 다르게 표기되는 사례(예: 신설 광역 지자체명 축약)는 실측을 거쳐 등록된 것만 공식 명칭과 동일하게 인정합니다(Provider Alias 정책) - 실측되지 않은 별칭은 추가하지 않습니다.
- Snapshot 파일이 없거나 손상되면 화면에 오류가 표시되고 "수집 시작" 버튼이 비활성화됩니다(다른 샘플 데이터로 조용히 대체되지 않습니다).
